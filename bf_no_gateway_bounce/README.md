# BF No Gateway Bounce

Stops Odoo's mail gateway from auto-replying to people who write to Blue Fox.

## The message this kills

> Dear Sender,
>
> The message below could not be accepted by the address contact@example.com.
> Please try again later or contact Example Inc. instead.
>
> Kind Regards

It is sent from `MAILER-DAEMON`, quotes the sender's own email back at them, and
tells them an address that *is* live and monitored refused their mail.

## Why a module and not a setting

There is no setting. The four call sites are hardcoded in core, and they all
funnel through one method, `mail.thread._routing_create_bounce_email`:

| Call site | Trigger |
| --- | --- |
| `mail_thread.message_route` | loop detection — same sender/thread hit too many times |
| `mail_thread.message_route` | someone writes directly to the catchall address |
| `mail_thread.message_route` | catchall plus other unroutable recipients |
| `mail_alias._alias_bounce_incoming_email` | alias misconfigured, or `alias_contact` rules rejected the sender |

This module overrides that single method to log at WARNING and return without
creating the `mail.mail`.

## What is deliberately left alone

- Core still sets `alias_status = 'invalid'` before calling us, so a broken
  alias is still visible under **Settings > Technical > Email > Aliases**.
- Core's `_routing_warn` still logs the routing failure.
- Inbound bounce *detection* (`_routing_handle_bounce`) — the code that records
  real delivery failures against partners and feeds the blacklist — is a
  separate path and is untouched.

The trade-off: a sender whose mail genuinely cannot be routed now gets silence
instead of a misleading refusal, and the alias creator no longer receives a
copy. The failure is still in the Odoo log and on the alias record.

## History

Added 2026-07-31 after a bounce went out to a supplier's support desk on a
ticket reply. Root cause was a separate bug in OCA `mail_autogenerated_header`
— its `_notify_thread` returns `False` where the `sms` module expects an
iterable of recipients, so `project.task` creation from an incoming alias
raised `TypeError: 'bool' object is not iterable`, rolled back, and tripped the
alias-invalid bounce. That bug is fixed separately; this module is the backstop
so no future routing failure can mail a sender again.

Earlier bounces in the same family went to two clients replying to calendar
invitations, which is what makes silence the right default here.
